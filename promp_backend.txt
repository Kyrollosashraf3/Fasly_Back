## 1. نظرة عامة على النظام (Overview)
--------------------------------------------------------------------------------
فاسلي (Fasly) نظام إدارة مدرسة الأحد (Sunday School) لكنيسة، يخدم متابعة الأولاد،
الحضور، الغياب، الاشتراكات في الرحلات، المتابعة الفردية، الإشعارات، والتقارير.

البنية:
- Back-end: FastAPI (Python) + PostgreSQL + SQLAlchemy ORM + JWT Auth + bcrypt
- Front-end: React (Vite) + JavaScript (JSX) + CSS مخصصة
- المنافذ: الخادم على 9001، وال واجهات على Vite dev server

## 3. الموديلات (Database Models)
--------------------------------------------------------------------------------
كل الجداول تحمل church_id للعزل بين الكنائس. السوبر أدمين يرى كل الكنائس، باقي الأدوار مقيدة بكنيستهم.

3.1 جدول users (الحسابات / تسجيل الدخول)
الحقول: id (PK), phone (varchar(20) unique), password_hash (varchar(255) nullable), role (enum), church_id (int FK), teacher_id (int FK nullable unique), boy_id (int FK nullable unique), created_at, updated_at
القيود (ck_users_role_owner):
- teacher/admin: teacher_id موجود، boy_id NULL، church_id موجود
- user: boy_id موجود، teacher_id NULL، church_id موجود
- general_admin: teacher_id موجود، boy_id NULL، church_id موجود
- abona: boy_id NULL، church_id موجود (teacher_id اختياري للعرض)
- super_admin: boy_id NULL، church_id اختياري (يرى كل الكنائس)
الخصائص المحسوبة: display_name (اسم المعلم أو الولد)، managed_class_ids (فصول أمين المرحلة)، pending_signup (True إذا password_hash NULL)

3.2 جدول boys (الأولاد)
الحقول: id (PK), boy_name, gender (m/f), birth_date, phone, phone_2, zone, address, latitude, longitude, father_name (enum nullable), national_id, skills (ARRAY text), class_id (int FK), last_visit_date, note, issue_flag (boolean default False), created_at, updated_at
العلاقات: church, class_, user (1:1), attends, follow_ups, groups, subscriptions, trip_attendances, task_values
الخصائص المحسوبة: teacher_id (من جدول المجموعات)، teacher_name (اسم الخادم من المجموعات)، age (محسوب من birth_date لا يُخزن)

3.3 جدول teachers (الخدام - ليس حساب تسجيل دخول)
الحقول: id (PK), teacher_name, birth_date, phone, phone_2, zone, address, latitude, longitude, class_id (int FK nullable), father_name (enum nullable), skills (ARRAY text), last_visit_date, note, created_at, updated_at
العلاقات: church, class_, user (1:1), groups, follow_ups, teacher_checks, task_values, trip_attendances, managed_classes

3.4 جدول trips (الرحلات)
الحقول: id (PK), name (varchar(200)), cost (int بالجنيه), class_id (int FK), created_at (date), status (varchar default 'active'), recorded_by (int FK users)

3.5 جدول subscriptions (الاشتراكات المالية)
الحقول: id (PK), boy_id (int FK), trip_id (int FK), type (enum charge/recover), value (int بالجنيه), note (varchar nullable), date (date nullable), created_at (datetime), created_by (int FK users nullable)
الفهارس: (trip_id, boy_id), (boy_id, created_at)

المنطق الحالي في المكون:
- الحالة: boys (قائمة الأولاد من getTripSummary، مصفاة registered), payments (دفعات الرحلة من getForTrip), usersMap (خريطة id → اسم display), search (نص البحث), boyId (معرف الولد المحدد)
- التحميل (useEffect عند تغيير tripId): SubscriptionAPI.getTripSummary(tripId), SubscriptionAPI.getForTrip(tripId), AuthAPI.users()
- التصفية: boys.filter((b) => b.registered) (فقط من سجل اسمهم في الرحلة)
- نتائج البحث: boys.filter((b) => b.boy_name?.includes(q))
- الولد المحدد: boys.find((b) => b.boy_id === boyId)
- تاريخ الدفعات: payments.filter((p) => String(p.boy_id) === String(boy.boy_id))
- العرض: حقل بحث بالنص (بدون منسدل)، كارت الولد يحتوي اسم الولد + شارة حالة (مكتمل/حجز اسم/جزئي)، مبالغ دفع/باقي/الإجمالي (ألفاظ عربية: دفع، باقي، الإجمالي)، teacher_name يظهر تحت اسم الولد (إذا وجد في usersMap، وإلا "غير معروف")
- usersMap يُبنى من AuthAPI.users() التي تستدعي GET /auth/users - يتم استخدام u.display_name || u.name || u.username || u.phone
- المفتاح في usersMap هو String(u.id) (تحويل إلى نص للمقارنة الآمنة)
- عند البحث عن teacher_name للولد: usersMap[String(boy.boy_id)] - افتراض أن معرف الحساب يتطابق مع معرف الولد (لأن حساب النوع user مرتبط بـ boy_id)

3. العزل متعدد المستأجرين: كل جدول يحمل church_id، والفحص يكون على مستوى الكنيسة أولاً
4. عدم وجود أداة ترحيل (Migration): create_tables() في database.py يضيف الأعمدة الناقصة تلقائياً عند التشغيل
5. الأرقام: المخزنة كـ int بالجنيه المصري (بدون كسور)
6. التواريخ: ISO format (YYYY-MM-DD) على الشبكة، تُنظَّم للعرض عبر format.js
7. أرقام الهواتف: تُخزّن بصيغة 01xxxxxxxxx بعد الت.Normalization عبر normalise_phone()
8. المصادقة: JWT Bearer token، ينتهي بعد 60 دقيقة، يُخزّن في localStorage في الفرونت إند
9. معالجة الأخطاء: الخدمات تُلقي HTTPException مع رمز حالة مناسب ورسالة عربية

## 15. تحديثات حديثة (تعدد الكنائس + خريطة الافتقاد + حفظ اللوكيشن + افتقاد الخدام)
--------------------------------------------------------------------------------
هذا القسم يوثّق التعديلات التي تمت بعد النسخة الأولى من هذا الملف. أي محادثة جديدة
تق رأسه أولاً لأنها تمس كل الطلبات تقريباً.

15.1 الفلتر العام للكنيسة (Global Church Filter)
- الفكرة: السوبر أدمين (مالك المنصة) يختار كنيسة من الهيدر، فيُضيّق كل شاشة وكل قراءة
  على تلك الكنيسة، بدون أن يعرف أي Route بذلك. التينانت (أي دور آخر) لا يستخدم الفلتر
  أبداً: يظل مربوطاً بـ users.church_id.
- التنفيذ في app/core/auth/deps.py:
  * _requested_church_id(request) يقرأ church_id من الـ query string أو الهيدر X-Church-Id،
    ويرفض القيمة غير الرقمية بـ 422.
  * get_current_user يضع القيمة على user.selected_church_id فقط لو role == SUPER_ADMIN.
    وهي صفة وقت التشغيل (transient attribute) وليست عموداً في قاعدة البيانات.
  * التينانت: أي قيمة قديمة في localStorage تُتجاهل تماماً، فلا يمكن نقله لكنيسة أخرى.
- app/core/data/common.py:
  * my_church_ids(user): None = كل الكنائس (سوبر أدمين بلا اختيار)، أو [selected] لو مختار،
    أو [user.church_id] للتينانت. حساب تينانت بلا church_id يرجع [] (لا يسرّب بيانات).
  * my_class_ids(db, user): يبني قائمة الفصول من نفس الكنيسة المختارة؛ السوبر أدمين المفلتر
    يرى فصول الكنيسة المختارة فقط. التينانت يتجاهل أي selected قديم.
  * target_church_id(db, user, requested, class_id=, person=): يحدد كنيسة الصف الجديد.
    التينانت لا يكتب لكنيسة غير كنيسته (403). السوبر أدمين: إن اختار كنيسة من الهيدر لا
    يستطيع الكتابة لكنيسة أخرى، والصف الجديد بلا church_id ينزل على الكنيسة المختارة أو
    الكنيسة الافتراضية.
  * scope_church(query, model, user): فلتر model.church_id.in_(my_church_ids).
  * ensure_my_church / ensure_boy_access / ensure_teacher_access: أصبحت تحترم الفلتر أيضاً،
    فالسوبر أدمين المفلتر على كنيسة يُرفض له صف من كنيسة أخرى (403 / 404 حسب الحالة).
  * scope_teachers / scope_follow_ups / scope_checks / scope_users: كلها تمر على نفس الفلتر.
- app/core/data/churches.py: ChurchService.query **يتعمد** تجاهل selected_church_id:
  السوبر أدمين يرى كل الكنائس دائماً حتى تُملأ قائمة الهيدر، والتينانت يرى كنيسته فقط.
  الإنشاء/التعديل/الحذف للسوبر أدمين فقط (restrict على الحذف يرجع 409 لو فيه بيانات).
- app/core/DA/dashboard.py و follow_up_performance.py: _classes() يستخدم scope_church،
  فأرقام لوحة المعلومات تتبع الكنيسة المختارة.
- app/core/data/map.py: استعلام أولاد النطاق group/class/all يمر على scope_church.
- app/core/notifications/service.py: status و history يحترمان selected_church_id.
- ملاحظة مهمة: مسارات القوائم (GET /boys, /teachers, ...) لا تعلن معامل church_id في
  تعريفها؛ الفلتر يحدث تلقائياً من الـ dependency. لا تُضف معاملاً لكل Route.

15.2 خريطة الافتقاد (Visit Map)
- المسار الرئيسي: GET /locations/map (app/routes/locations.py) -> VisitMapService.route
  في app/core/data/map.py.
- المعاملات:
  * latitude/longitude: موقع الخادم الآن (اختياري). لو غاب، يبدأ المسار من أول بيت
    (origin.source = "first_house")، ولو حضر فالمصدر "client".
  * scope: group (مجموعة خادم) | class (فصل) | all (كل الفصول المسموحة). الافتراضي class.
  * teacher_id: لتضييق مجموعة خادم معين (للأمين).
  * class_id: تضييق على فصل واحد.
  * name / zone / address: فلاتر نصية (name و address بحث جزئي، zone مطابقة).
  * person_type: boys (افتراضي) | teachers. خريطة الخدام مسموحة للمديرين فقط
    (MANAGERS)، وإلا 403.
- الاستجابة MapRouteResponse تحتوي كل ما تحتاجه الشاشة في نداء واحد:
  * houses: مرتبة الأقرب فالأقرب (nearest_neighbour في app/core/geo.py)، وكل بيت فيه
    person_id/person_name + boy_id/boy_name أو teacher_id/teacher_name، الإحداثيات،
    has_coordinates، العنوان والمنطقة، الهاتف، whatsapp_url و call_url جاهزين للفتح،
    آخر افتقاد وعدده، prefill جاهز لـ POST /follow-ups، وأعلام can_record_location /
    can_follow_up.
  * unlocated: نفس الشكل لكن بلا إحداثيات (يجب حفظ اللوكيشن أولاً).
  * origin + legs + polyline: نقاط الرسم [[lat,lng],...] تبدأ من origin، وكل leg فيه
    المسافة بالمتر/كم ودقائق المشي.
  * summary: total_boys/total_people، located، unlocated، visited_today، coverage_percent.
  * total_distance_m/km و total_walk_minutes و ordered_boy_ids/ordered_person_ids.
- أرقام الهاتف تُحوَّل في map.py (_digits) إلى 20xxxxxxxxxx لبناء روابط wa.me و tel.
- الصلاحيات: نفس scope_boys / scope_teachers + الفلتر الكنسي، فالخادم يرى مجموعته،
  الأمين فصله/مرحلته، وأبونا كل فصول كنيسته.
- لا يوجد جدول إحداثيات منفصل: نقطة البيت هي boys.latitude/longitude ونقطة الخادم هي
  teachers.latitude/longitude.

15.3 حفظ اللوكيشن (Location saving)
- الخدمات: BoyLocationService و TeacherLocationService في app/core/data/locations.py.
- نقاط البيت تُكتب مباشرة على صف الولد (boys.latitude/longitude)، وكذلك الخادم على
  teachers.latitude/longitude. لا جدول locations منفصل.
- POST /locations/boys/{boy_id}: أي موظف يرى الولد (ensure_boy_access). يُحدّث updated_at.
  إن أرسل العميل status (FollowEnum) تُكتب أيضاً متابعة في follow_ups في نفس المعاملة،
  بشرط وجود خادم للمجموعة؛ غير ذلك 400 مع رسالة عربية واضحة.
- POST /locations/boys/me: لحساب الولد نفسه فقط (role USER و boy_id موجود)، ولا يكتب
  متابعة أبداً.
- GET /locations/boys/{boy_id}/current: يرجع النقطة الحالية أو null لو لم تُسجل.
- POST /locations/teachers/{teacher_id}: لتسجيل موقع الخادم (يُستخدم في خريطة الخدام).
- التينانت محمي: ensure_boy_access/ensure_teacher_access تمنع أي ولد أو خادم من كنيسة
  أخرى، وكذلك تمنع السوبر أدمين المفلتر على كنيسة أخرى.

15.4 افتقاد الخدام (Servant follow-up)
- جدول teacher_follow_ups + مسارات /teacher-follow-ups (GET/POST/GET/PATCH/DELETE).
- نفس نمط متابعة الأولاد: status من FollowEnum، action_date، note، recorded_by،
  church_id، وclass_id كنسخة تاريخية.
- يظهر في خريطة الافتقاد عند person_type=teachers: آخر افتقاد، عدده، visited_today،
  وروابط الاتصال. منع الرؤية/الكتابة يمر على scope_checks/ensure_teacher_access
  والفلتر الكنسي.
