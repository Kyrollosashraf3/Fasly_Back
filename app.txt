الغرض من هذا الجزء
------------------
الجزء اللي فوق كان المواصفة الأصلية للمشروع. اللي تحته مرجع للفريق: يشرح كل
موديول موجود دلوقتي، إيه المسؤولية بتاعته، وإزاي بيتكلم مع غيره. اعتبره دليل
سريع لأي مطور جديد، ومرجع ثابت لما نرجع للكود بعد شهور. القاعدة الحاكمة:
الصلاحية أو الحساب أو التحويل لا يتكرر في أكتر من مكان - لكل سؤال بيت في مكان
واحد بس. لو محتاج تضيف حاجة، ابحث عن المكان المخصص ليها في الخريطة في القسم 2.


1) الفكرة العامة والطبقات  -  Architecture
-------------------------------------------
الباك إند FastAPI + SQLAlchemy + PostgreSQL. الواجهة (React) موجودة في مشروع
منفصل (front_fasly) بتتكلم معانا over HTTP. التطبيق دلوقتي SaaS: قاعدة بيانات
واحدة تستضيف كنائس كتير، وكل كنيسة «سيلو» منفصل عن التاني.

الطبقات من فوق لتحت:

    routes/         -> HTTP بس: parser، تحقق من الشكل، استدعاء الخدمة. مفيش قرار صلاحية هنا.
    schemas/        -> شكل الطلب والرد (Pydantic). مفيش منطق أعمال.
    core/data/      -> الخدمات: لكل جدول service. كل سؤال بيسأله في مكانه.
    core/DA/        -> تحليلات/تقارير (Data Analysis): قراءة فقط وتجميع في Python.
    core/EDA/       -> Excel: قراءة/كتابة ملفات، قوالب، وتصدير.
    core/notifications/ -> Web push: من ياخد الإشعار، ومين بعت، والرسائل المجدولة.
    core/auth/      -> تسجيل الدخول، الهوية، الـ seed عند التشغيل، تحديد معدل الطلبات.
    core/app.py     -> مصنع التطبيق: يجمع كل حاجة ويربط الـ routers والـ lifespan.
    core/geo.py     -> حسابات المسافة والطريق (بدون خدمة خارجية).
    core/middleware.py -> لوج لكل طلب.
    models/         -> ORM: هو الـ schema نفسه (مفيش أداة migrations).
    db/database.py  -> الـ engine والجلسة وترقية الـ schema عند التشغيل.
    config/         -> الإعدادات واللوجر.

قاعدة ذهبية: route ما ياخدش قرار، service ما يكررش قاعدة صلاحية، والصلاحية
كلها في core/data/common.py.

3) دورة حياة الطلب  -  Request lifecycle
-----------------------------------------
    1. الطلب يدخل RequestLogMiddleware (يسجل المستخدم والزمن والمسار).
    2. CORS + slowapi limiter (الـ login محدد بمعدل حسب رقم التليفون).
    3. الـ route يفك الـ JSON عبر Pydantic schema (الشكل بس).
    4. get_current_user يقرأ الـ Bearer JWT ويرجع صف User الحقيقي من DB.
    5. الـ route يستدعي Service(db, current_user).method(data).
    6. الخدمة تسأل common.py عن الصلاحية (الكنيسة أولاً، ثم الفصل)،
       تكتب الـ church_id، وتعمل commit، وترجع الـ ORM row.
    7. Pydantic يحوّل الـ row إلى Response (from_attributes=True).
    8. الـ middleware يطبع سطر اللوج.

ملاحظة: الخدمة بتاخد الـ User الحي مش نسخة منه، فـ role/church_id دايمًا
من الـ DB في لحظة الطلب.


4) نموذج تعدد الكنائس والصلاحيات  -  Tenancy & permissions
----------------------------------------------------------
المبدأ: «كل أمين عام يشوف كنيسته فقط». السؤال الأول في أي عملية: هل الصف ده
من كنيستي؟ وبعدين: هل الفصل بتاعي؟ مفيش استثناء - حتى لو حد خمّن class_id
من كنيسة تانية، الـ 403 تيجي قبل أي قراءة أو كتابة.

الأدوار (RoleEnum في app/models/enums.py):

    الدور            المعنى                          النطاق
    --------------  -------------------------------  --------------------------------
    user            ولد في الخدمة                    بياناته هو فقط
    teacher         خادم/أستاذ                       نفسه + أولاد فصله (حضور/تعديل/إضافة)
    admin           أمين فصل                         كل الخدام والأولاد في فصله
    general_admin   أمين مرحلة                       مجموعة فصول من general_admin_classes
    abona           أبونا / أمين الكنيسة             كل الفصول والمراحل في كنيسته فقط
    super_admin     صاحب المنصة/المطور                كل الكنائس ( church_id = NULL )

قواعد الـ tenant:

    * كل جدول بيانات/لوج فيه church_id (ما عدا churches نفسه).
    * القيد: NOT NULL في كل الجداول إلا users - الـ super_admin بس church_id NULL.
    * كل church_id FK على churches(id) مع ON DELETE RESTRICT: كنيسة ليها بيانات
      ما تتمسحش؛ لازم تمسح بياناتها أولاً (الخدمة بترجع 409 واضح).
    * أرقام التليفونات فريدة globally (مش لكل كنيسة) - ما تتحولش لفريد لكل كنيسة.
    * الإشعارات: dedupe_key فريد لكل كنيسة (church_id, dedupe_key)، والتجميع
      بيحصل على (church_id, class_id) عشان كنيستين يقدروا يبعتوا نفس التذكير
      في نفس اليوم.

أهم دوال common.py (المرجع الوحيد للصلاحية):

    is_manager(user)              صحيح لأي أمين (admin/general_admin/abona/owner)
    my_church_ids(user)           كنائس المستخدم؛ None = كلها (owner بس)
    my_class_ids(db, user)        فصول المستخدم؛ None = كلها (owner بس).
                                  أبونا ياخد كل فصول كنيسته (قائمة مش None).
    target_church_id(...)         كنيسة الصف الجديد: المستخدم متثبت لكنيسته،
                                  والـ owner يقدر يختار أو يستنتج من الفصل/الشخص
                                  أو يرجع للكنيسة الافتراضية.
    ensure_my_church(...)         403 لو الكنيسة مش بتاعته  (يُندى أولاً)
    ensure_my_class(...)          403 لو الفصل مش من فصوله  (الكنيسة تُفحص أولاً)
    ensure_boy_access / ensure_teacher_access    الولد/الخادم يشوف نفسه بس
    scope_church / scope_classes / scope_boys / scope_teachers /
    scope_follow_ups / scope_checks / scope_users  فلترة الـ query حسب النطاق
    get_or_404 · commit · ensure_unique · ensure_name_free ·

    ClassService     القراءة مفتوحة (اسم الفصل ما بيسربش حاجة)، الإنشاء/التعديل
                     لأمين الفصل أو الـ owner. كل create بياخد church_id.
    TeacherService   دليل الخدام. الـ login بيتعمل في UserService ويرجع عبر
                     users.teacher_id.
    BoyService       owner كل | admin/teacher فصلهم | الولد نفسه. مفيش صف
                     جديد من غير فحص الاسم (names.py).
    GroupsService    owner كل | أي أمين فصوله | خادم مجموعته. شاشة المجموعة
                     بتضيف نسبة الحضور وآخر افتقاد لكل ولد.
    AttendanceService / TeacherCheckService  كشف الجمعة: bulk save لكل الفصل
                     في transaction واحدة.
    FollowUpService  تسجيل افتقاد: class_id snapshot + recorded_by.
    BoyLocationService / VisitMapService      حفظ إحداثيات البيت والخريطة
                     (تفاصيل في قسم 11).
    TaskService / TaskValueService / TripService / SubscriptionService
                     المسابقات والتسميعات والرحلات والاشتراكات (بالعربية في الكود،
                     بنفس نمط الصلاحية: owner > أمين مرحلة > أمين فصل > خادم > ولد).
    UserService      الحسابات: التسجيل برقم تليفون، class_ids لأمين المرحلة،
                     منع رفع role أو_abona لغير الـ owner، منع نقل حساب بين كنائس
                     لغير الـ owner. signup_check / complete_signup على مستوى الموديول
                     (بيشتغلوا قبل الدخول).
    names.py         مقارنة الأسماء العربية: normalise / signature / similarity /
                     matches_for / ensure_full_name / ensure_name_addable.
                     المسؤول الوحيد عن «هل ده نفس الولد؟».

15) إزاي تضيف موديول جديد  -  How-to
-------------------------------------
    1. models/<table>.py  -> عرّف الـ class (كل جدول بيانات لازم church_id + FK)
                             وسجّله في models/__init__.py (__all__).
    2. schemas/<table>.py -> Create / Update / Response (ورّث ORMResponse).
                             سجّلها في schemas/__init__.py.
    3. core/data/<table>.py -> Service(BaseService): query() تبدأ بـ scope_*/church،
                             create/update/delete بيستدعي target_church_id و commit.
                             صدّرها في core/data/__init__.py.
    4. routes/<table>.py  -> APIRouter(prefix=...)، كل endpoint يستدعي الخدمة.
                             أضف الـ router في routes/__init__.py و core/app.py.
    5. db/database.py      -> لو الجدول قديم، أضف خطوة ALTER في create_tables()
                             وظيرها في church.txt (نفس الترتيب).
    6. DA/EDA              -> لو فيه تقرير أو إكسيل، المكان core/DA أو core/EDA.
    7. اختبر: compileall + OpenAPI + smoke (الأوامر في قسم 17).


16) نقاط مهمة ومخاطر  -  Gotchas
--------------------------------
    * class_id في attend/follow_up/teacher_check/task_value/trip/subscription
      snapshot تاريخي - ما تعدّلهوش بأي تعديل لاحق على الولد.
    * users.church_id nullable بالقصد (super_admin بس). أي محاولة تخليه NOT NULL
      لازم تستثني الـ owner.
    * ALTER TYPE ... ADD VALUE على PostgreSQL القديم محتاج commit منفصل؛
      church.txt مكتوب مع Auto-commit عشان كده.
    * إضافة حقل enum للـ CHECK constraint في نفس transaction على PG 12+ تمام،
      وإصدارات أقدم محتاجة تشغيل القسم 8/9 تاني.
    * مفيش LocationSourceEnum / has_whatsapp / جدول location - لا تضيفهم.
    * dedupe_key لازم يتضمن church_id، وإلا كنيستين هيقطعوا إشعارات بعض.
    * الأرقام فريدة globally - ما تعملش unique (church_id, phone).
    * حذف كنيسة فيه بيانات بيرجع 409 (ON DELETE RESTRICT) - ده سلوك مقصود.
    * smoke tests على SQLite محتاجة تستبدل ARRAY بـ JSON في boys.skills و
      teachers.skills (الـ ARRAY نوع PostgreSQL).

    لغة الكود: تعليقات بالعربية في مجالات المسابقات والاشتراكات، وبالإنجليزية في
    الباقي. فضّل نفس نمط الملف اللي بتعدّل عليه.
